# M2-2 - Lesson 01: Kiểu dữ liệu và constraint

> **Mục tiêu:** nhìn một `CREATE TABLE` và giải thích được cột lưu gì, quy tắc nào chặn dữ liệu sai, và một thao tác ghi hợp lệ hay bị từ chối. Bài này **chưa** yêu cầu dựng PostgreSQL, viết repository hay nhớ mã lỗi database.

## 1. Từ M2-1 sang M2-2: đọc đúng chưa đủ

M2-1 hỏi: "`SELECT` này trả những dòng nào?" M2-2 hỏi thêm: "Một dòng sai có được vào database không? Nếu đã vào, ai bảo đảm dữ liệu vẫn đúng?"

Ví dụ Product có giá `-100`. Controller có thể kiểm tra request, nhưng dữ liệu còn có thể đến từ script SQL, job nhập dữ liệu, hoặc một đường code khác. **Constraint của database bảo vệ dữ liệu tại nơi lưu trữ**, bất kể ai gửi lệnh ghi. Validation trong Java vẫn hữu ích để báo lỗi thân thiện sớm; hai lớp bảo vệ này bổ sung cho nhau. [PostgreSQL: Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html).

```text
HTTP request -> DTO validation -> Service/JPA -> SQL -> PostgreSQL constraint
                   |                                   |
              báo lỗi sớm                     từ chối dữ liệu vi phạm
```

DB chặn lệnh ghi không tự quyết định API phải trả `400` hay `409`: HTTP status phụ thuộc cách ứng dụng xử lý exception. Lesson này chỉ tập trung vào **quy tắc của DB**.

## 2. Schema xuyên suốt bài

Đây là **schema minh họa** cho hai bảng bạn đã dùng trong M2-1, không khẳng định code hiện tại của `shopcore` đang có schema này:

```sql
CREATE TABLE categories (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name TEXT NOT NULL UNIQUE
);

CREATE TABLE products (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    sku TEXT NOT NULL UNIQUE,
    name TEXT NOT NULL,
    price NUMERIC(12, 2) NOT NULL CHECK (price > 0),
    category_id BIGINT REFERENCES categories(id),
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    attributes JSONB
);
```

Đọc thành lời:

- Mỗi Category/Product có `id` định danh; khi bỏ qua `id` lúc thêm dòng, database có thể sinh giá trị.
- `sku` của Product bắt buộc có và không được trùng.
- `price` bắt buộc có và phải lớn hơn 0.
- `category_id` có thể chưa có (`NULL`); nếu có giá trị thì phải trỏ tới một Category tồn tại.
- `created_at` có giá trị mặc định nếu không được cung cấp.
- `attributes` là dữ liệu JSON tùy chọn, không thay thế các cột cốt lõi.

**Mẹo đọc schema:** với từng cột, hỏi liên tiếp: kiểu gì? được `NULL` không? có default không? quy tắc nào ràng buộc nó? có tham chiếu bảng khác không?

## 3. Chọn kiểu dữ liệu theo ý nghĩa

| Kiểu | Trong schema | Vì sao chọn? | Điều không nên hiểu nhầm |
|---|---|---|---|
| `BIGINT` | `id`, `category_id` | Số nguyên làm khóa | `BIGINT` tự nó **không** là PK/FK và không tự tăng |
| `TEXT` | `sku`, `name` | Chuỗi ký tự | `TEXT` tự nó không cấm chuỗi rỗng; `NOT NULL` chỉ cấm `NULL` |
| `NUMERIC(12,2)` | `price` | Số thập phân chính xác, phù hợp giá tiền | Kiểu dữ liệu không tự cấm số âm; cần `CHECK` |
| `TIMESTAMPTZ` | `created_at` | Thời điểm có ngữ nghĩa múi giờ | Không lưu lại tên múi giờ gốc; PostgreSQL quy đổi khi lưu/hiển thị theo múi giờ session |
| `JSONB` | `attributes` | Thuộc tính biến thiên, ví dụ `{ "color": "black" }` | Không nên giấu `sku`, `price`, FK quan trọng vào JSONB chỉ vì tiện |
| `UUID` | Chưa dùng trong schema trên | ID khó đoán hơn/được tạo phân tán khi bài toán cần | Không bắt buộc mọi bảng phải đổi từ `BIGINT` sang UUID |

`NUMERIC(12,2)` có tối đa 12 chữ số tổng, trong đó 2 chữ số sau dấu thập phân. PostgreSQL khuyến nghị `numeric` khi cần độ chính xác như tiền; `double precision` là số dấu phẩy động, không phù hợp khi yêu cầu kết quả thập phân chính xác. [PostgreSQL: Numeric Types](https://www.postgresql.org/docs/current/datatype-numeric.html).

`TIMESTAMPTZ` lưu thời điểm được chuẩn hóa; khi hiển thị sẽ theo múi giờ của session. Nó **không giữ lại** múi giờ gốc của người gửi. [PostgreSQL: Date/Time Types](https://www.postgresql.org/docs/current/datatype-datetime.html).

`JSONB` lưu JSON đã xử lý để truy vấn hiệu quả; không giữ nguyên thứ tự key hoặc khoảng trắng đầu vào. Dùng cho dữ liệu linh hoạt, còn field phải lọc/ràng buộc thường xuyên thì cột quan hệ rõ ràng vẫn dễ quản lý hơn. [PostgreSQL: JSON Types](https://www.postgresql.org/docs/current/datatype-json.html).

## 4. Constraint: mỗi loại chặn một kiểu sai

### 4.1. `PRIMARY KEY` - dòng nào là dòng nào?

```sql
id BIGINT PRIMARY KEY
```

PK vừa **duy nhất** vừa **không `NULL`**. Hai Product không thể có cùng id. `BIGINT` chỉ là kiểu; chính `PRIMARY KEY` mới áp quy tắc này. [PostgreSQL: Constraints - Primary Keys](https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-PRIMARY-KEYS).

### 4.2. `IDENTITY` - id được sinh như thế nào?

```sql
id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
```

`IDENTITY` dùng sequence ngầm để sinh id khi lệnh thêm dòng **không cung cấp id**. `BY DEFAULT` vẫn cho phép cung cấp id tường minh; nếu làm vậy mà trùng, **PK** sẽ chặn. Vì thế `IDENTITY` và PK giải quyết **hai việc khác nhau**: *sinh giá trị* và *bảo đảm duy nhất/không NULL*. Lesson 04 sẽ nhắc lại sequence; bây giờ chỉ cần nhận diện. [PostgreSQL: Identity Columns](https://www.postgresql.org/docs/current/ddl-identity-columns.html).

### 4.3. `NOT NULL` - bắt buộc có giá trị

```sql
name TEXT NOT NULL
```

Không được ghi `name = NULL`. Nhưng `name = ''` là **chuỗi rỗng**, không phải NULL; `NOT NULL` vẫn cho qua. Nếu nghiệp vụ cấm rỗng, cần validation hoặc ràng buộc bổ sung. [PostgreSQL: Constraints - Not-Null](https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-NOT-NULL).

### 4.4. `UNIQUE` - không trùng giữa các dòng

```sql
sku TEXT NOT NULL UNIQUE
```

Hai Product không được có cùng SKU. `sku` ở đây còn có `NOT NULL`, nên không có trường hợp SKU trống vì `NULL`.

**Bẫy quan trọng:** nếu chỉ viết `sku TEXT UNIQUE` (không có `NOT NULL`), PostgreSQL mặc định có thể cho **nhiều dòng `sku = NULL`**. `UNIQUE` không mặc nhiên có nghĩa cột bắt buộc có giá trị. Có tùy chọn `NULLS NOT DISTINCT` để thay đổi quy tắc này, nhưng chưa cần dùng ở lesson này. [PostgreSQL: Constraints - Unique](https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-UNIQUE).

### 4.5. `CHECK` - biểu thức phải không được FALSE

```sql
price NUMERIC(12,2) NOT NULL CHECK (price > 0)
```

- Giá `100.00`: qua.
- Giá `0` hoặc `-5`: bị `CHECK` chặn.
- Giá `NULL`: bị **`NOT NULL`** chặn.

Tại sao cần cả `NOT NULL`? Trong PostgreSQL, `CHECK` được xem là thỏa khi biểu thức là TRUE **hoặc NULL**. Chỉ `CHECK (price > 0)` thì `price=NULL` không bị CHECK chặn. [PostgreSQL: Constraints - Check](https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-CHECK-CONSTRAINTS).

### 4.6. `FOREIGN KEY` - tham chiếu phải hợp lệ

```sql
category_id BIGINT REFERENCES categories(id)
```

Nếu `category_id=2`, DB cần có `categories.id=2`; nếu không có sẽ từ chối. Vì cột này **không có `NOT NULL`**, `category_id=NULL` được phép: Product chưa được gán Category. Đây là FK tùy chọn. Nếu nghiệp vụ bắt Product luôn có Category, thêm `NOT NULL` vào `category_id`. [PostgreSQL: Constraints - Foreign Keys](https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-FK).

**Chú ý khi xóa Category:** FK còn tác động tới xóa/sửa hàng được tham chiếu; mặc định không thể xóa Category đang được Product tham chiếu nếu không cấu hình hành vi phù hợp. Phần thao tác `DELETE` học ở Lesson 02.

## 5. Dự đoán DB nhận hay từ chối

Giả sử `categories` đã có `(1, 'Books')` và `(2, 'Electronics')`; `products` đã có SKU `BK-01`, giá `120.00`, `category_id=1`. Với schema ở mục 2:

| Dữ liệu Product mới | DB xử lý | Vì sao? |
|---|---|---|
| `sku='EL-02', name='Mouse', price=300, category_id=2` | Nhận | Có SKU mới, giá dương, Category 2 tồn tại |
| `sku='BK-01', name='Another book', price=80, category_id=1` | Từ chối | `UNIQUE(sku)` |
| `sku='BK-02', name='Book', price=0, category_id=1` | Từ chối | `CHECK (price > 0)` |
| `sku='BK-03', name='Book', price=NULL, category_id=1` | Từ chối | `NOT NULL(price)` |
| `sku='BK-04', name='Book', price=50, category_id=999` | Từ chối | FK: Category 999 không tồn tại |
| `sku='BK-05', name='Book', price=50, category_id=NULL` | Nhận | FK tùy chọn vì cột cho `NULL` |
| `sku=NULL, name='Book', price=50, category_id=1` | Từ chối | `NOT NULL(sku)` |

Các hàng này là **tình huống độc lập**, không phải bảy lệnh nối tiếp trên cùng database. Khi dự đoán, luôn chỉ ra **constraint cụ thể**, đừng chỉ nói "lỗi dữ liệu".

## 6. Đi từ request đến constraint

Ví dụ API tạo Product, request có `sku='BK-01'` đã tồn tại:

```text
JSON -> CreateProductRequest -> @Valid (nếu app có cấu hình)
  -> Controller -> Service -> JPA tạo INSERT -> PostgreSQL kiểm tra UNIQUE
  -> DB từ chối nếu trùng -> ứng dụng nhận exception -> handler quyết định response
```

Nếu Service tự gọi `existsBySku` trước khi insert, đó là kiểm tra giúp thông báo sớm, **không thay thế `UNIQUE` ở DB**: hai request đồng thời có thể cùng thấy "chưa tồn tại" rồi cùng thử insert. DB constraint là chốt chặn cuối. Không tự khẳng định mọi vi phạm đều thành một HTTP status cố định nếu chưa xem `GlobalExceptionHandler`. [PostgreSQL: Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html).

## 7. Bốn phân biệt phải thuộc bằng hiểu

```text
Kiểu dữ liệu  = giá trị có dạng gì?
Constraint   = giá trị/dòng có hợp lệ theo quy tắc không?
IDENTITY     = tạo id mặc định bằng sequence.
PRIMARY KEY  = id duy nhất và không NULL.
```

```text
NOT NULL     != không được là chuỗi rỗng.
UNIQUE       != bắt buộc NOT NULL.
CHECK(x > 0) != tự chặn NULL.
FOREIGN KEY  != bắt buộc có Category nếu cột FK cho NULL.
```

## 8. Tự luyện trước khi thi

2. Vì sao `sku TEXT UNIQUE` có thể cho nhiều `NULL`, còn `sku TEXT NOT NULL UNIQUE` thì không?
3. `category_id=999` và `category_id=NULL` khác nhau ra sao khi FK tùy chọn?
4. Nếu `IDENTITY` sinh id, tại sao còn cần PK?
5. Giá `NULL` có bị `CHECK (price > 0)` tự chặn không?
