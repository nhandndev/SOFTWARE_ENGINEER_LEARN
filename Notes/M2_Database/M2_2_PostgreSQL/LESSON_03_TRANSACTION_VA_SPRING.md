# M2-2 - Lesson 03: Transaction trong PostgreSQL và Spring

> **Mục tiêu:** tự kể được chuyện gì xảy ra với *hai thao tác ghi phụ thuộc nhau* khi thành công hoặc thất bại; biết `BEGIN`/`COMMIT`/`ROLLBACK` tương ứng với ranh giới `@Transactional` ở Service. Bài này tập trung vào tính **cùng thành công hoặc cùng hủy**, chưa đi sâu isolation level hay xử lý giao dịch phân tán.

## 1. Từ Lesson 02 đến vấn đề mới

Lesson 02 đã dạy: một `INSERT`/`UPDATE`/`DELETE` chọn dòng nào, thành công hay bị constraint chặn. Nhưng một việc của người dùng thường cần **nhiều lệnh**.

Ví dụ yêu cầu: "Tạo Category *Stationery*, rồi thêm Product *Pen* thuộc Category mới". Nghiệp vụ muốn:

```text
Thành công: có cả Category và Product.
Thất bại: không có cái nào.
```

Nếu Category được lưu rồi Product lỗi giá, việc còn lại Category trống có thể trái ý định. **Transaction đặt nhiều bước thành một đơn vị công việc**: tất cả cùng được xác nhận, hoặc cùng bị hủy. Transaction không làm một câu SQL sai trở thành đúng; constraint của Lesson 01 vẫn kiểm tra từng lệnh. [PostgreSQL: Transactions](https://www.postgresql.org/docs/current/tutorial-transactions.html).

## 2. Schema và dữ liệu cố định của bài

Đây là schema **giả định để học**, không khẳng định database hiện tại của `shopcore` đã có đúng cấu trúc này:

```sql
CREATE TABLE categories (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name TEXT NOT NULL UNIQUE
);

CREATE TABLE products (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    sku TEXT NOT NULL UNIQUE,
    name TEXT NOT NULL,
    price NUMERIC(12,2) NOT NULL CHECK (price > 0),
    category_id BIGINT REFERENCES categories(id)
);
```

Ban đầu chỉ có:

| Bảng | Dòng |
|---|---|
| `categories` | `(1, 'Books')`, `(2, 'Electronics')` |
| `products` | `(10, 'BK-01', 'Java Book', 120.00, 1)` |

Ở ví dụ SQL dưới đây, ta **cố ý ghi `id=3`** cho Category mới để dễ theo dõi. Schema dùng `GENERATED BY DEFAULT`, cho phép cung cấp id tường minh; trong ứng dụng thật, thường để DB sinh id và lấy lại bằng `RETURNING` hoặc qua JPA. Mỗi tình huống độc lập lại bắt đầu từ dữ liệu ban đầu trên, trừ khi nói rõ là chạy nối tiếp.

## 3. Không có `BEGIN`: mỗi câu tự hoàn tất

```sql
INSERT INTO categories (id, name) VALUES (3, 'Stationery');

INSERT INTO products (sku, name, price, category_id)
VALUES ('ST-01', 'Pen', 0, 3);  -- lỗi CHECK (price > 0)
```

Trong chế độ mặc định khi không mở transaction tường minh, lệnh đầu thành công và được commit riêng; lệnh thứ hai thất bại và bị rollback riêng. Kết quả: **Category 3 còn, Product ST-01 không có**. Hai câu SQL riêng lẻ không tự được gom thành "một việc" chỉ vì chúng nằm cạnh nhau trong file hoặc cùng một HTTP request. [PostgreSQL: `BEGIN`](https://www.postgresql.org/docs/current/sql-begin.html).

**Lưu ý:** JDBC/Spring có thể điều khiển transaction giúp bạn, nên đừng dựa vào việc có thấy chữ `BEGIN` trong Java hay không để kết luận ứng dụng không có transaction. Hãy xác định **ranh giới transaction thực tế**. [PostgreSQL: Transactions](https://www.postgresql.org/docs/current/tutorial-transactions.html).

## 4. Có `BEGIN`: một nhóm cùng thành công hoặc cùng hủy

### Trường hợp thành công

```sql
BEGIN;

INSERT INTO categories (id, name) VALUES (3, 'Stationery');

INSERT INTO products (sku, name, price, category_id)
VALUES ('ST-01', 'Pen', 15.00, 3);

COMMIT;
```

Sau `COMMIT`, Category 3 và Product ST-01 đều tồn tại. Khi transaction còn mở, chính session đang làm việc có thể thấy các thay đổi của mình; session khác **không thấy phần chưa commit**. Sau commit, cả nhóm thay đổi trở nên khả kiến với session khác theo quy tắc transaction của PostgreSQL. [PostgreSQL: Transactions](https://www.postgresql.org/docs/current/tutorial-transactions.html).

### Trường hợp chủ động hủy

```sql
BEGIN;
INSERT INTO categories (id, name) VALUES (3, 'Stationery');
INSERT INTO products (sku, name, price, category_id)
VALUES ('ST-01', 'Pen', 15.00, 3);
ROLLBACK;
```

Hai lệnh `INSERT` đã chạy trong transaction nhưng sau `ROLLBACK` **không còn tác dụng** trong database. Vì vậy "lệnh SQL chạy thành công" chưa đồng nghĩa "dữ liệu đã được commit". [PostgreSQL: Transactions](https://www.postgresql.org/docs/current/tutorial-transactions.html).

### Trường hợp lệnh thứ hai lỗi

```sql
BEGIN;
INSERT INTO categories (id, name) VALUES (3, 'Stationery');
INSERT INTO products (sku, name, price, category_id)
VALUES ('ST-01', 'Pen', 0, 3);  -- lỗi CHECK
ROLLBACK;
```

Product bị `CHECK` từ chối. Transaction đang mở chuyển sang **trạng thái lỗi**; các lệnh thông thường tiếp theo không thể tiếp tục như chưa có gì xảy ra. `ROLLBACK` hủy cả thay đổi Category trước đó. Muốn tiếp tục một phần sau lỗi cần savepoint, nhưng đó là công cụ nâng cao, không phải cách mặc định để che lỗi dữ liệu. [PostgreSQL: Transactions](https://www.postgresql.org/docs/current/tutorial-transactions.html).

## 5. Đọc luồng theo thời gian, không theo số dòng code

```text
Client gửi yêu cầu tạo cặp Category + Product
  -> Service bắt đầu một transaction
  -> Repository lưu Category
  -> Repository lưu Product
  -> không lỗi: COMMIT | có lỗi cần rollback: ROLLBACK
  -> Controller trả response theo kết quả
```

Ý nghĩa từng đoạn:

1. **Client/Controller** nói việc cần làm, không tự biến hai repository call thành một transaction.
2. **Service** là nơi biết hai thao tác thuộc cùng một nghiệp vụ, nên thường đặt ranh giới transaction ở method Service.
3. **Repository/JPA** thực hiện công việc lưu trữ bên trong ranh giới đó; lệnh SQL thực tế có thể được gửi khi `flush` hoặc ngay trước commit, không nhất thiết đúng tại dòng `save()`.
4. **Transaction manager** quyết định commit hay rollback khi method kết thúc/exception thoát ra; sau đó ứng dụng mới hoàn thành response.

Vì thế `repository.save()` trả về **không chứng minh** dữ liệu đã được commit. Nó có thể mới nằm trong persistence context hoặc đã gửi SQL nhưng transaction vẫn còn mở. [Spring: Transaction proxy](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/tx-decl-explained.html), [PostgreSQL: Transactions](https://www.postgresql.org/docs/current/tutorial-transactions.html).

## 6. `@Transactional` trong Spring làm gì?

Trong [mini project JPA M1-3](../../../m1-3-jpa-mini-project/src/main/java/com/shopcore/product/ProductService.java), bạn đã đặt `@Transactional` ở `ProductService.create/update/delete`. Đây là nơi phù hợp để nối kiến thức Java đã code với SQL đang học.

Ví dụ **mã phác họa** (không phải class có thể copy chạy ngay):

```java
@Service
class CatalogService {
    private final CategoryRepository categories;
    private final ProductRepository products;

    @Transactional
    public void createCategoryAndProduct() {
        Category category = categories.save(new Category("Stationery"));
        products.save(new Product("ST-01", "Pen", new BigDecimal("15.00"), category));
    }
}
```

Giả định constructor/entity ở đây chỉ minh họa. Khi **một bean khác** gọi method công khai qua Spring proxy, luồng khái niệm là:

```text
Controller -> proxy của CatalogService
           -> TransactionInterceptor / TransactionManager mở hoặc tham gia transaction
           -> CatalogService.createCategoryAndProduct()
           -> repositories/JPA thực hiện hai thao tác
           -> method kết thúc bình thường: commit
           -> exception thỏa quy tắc rollback thoát ra: rollback
```

`@Transactional` là **metadata để Spring áp dụng ranh giới**, không phải Java tự chèn chữ `BEGIN` và `COMMIT` vào source code. Mặc định propagation là `REQUIRED`: có transaction phù hợp thì tham gia, chưa có thì mở mới. [Spring: `@Transactional`](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html), [Spring: Transaction proxy](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/tx-decl-explained.html).

## 7. Exception nào khiến Spring rollback?

Trong cấu hình mặc định thường dùng của Spring:

- `RuntimeException` hoặc `Error` **thoát ra khỏi transactional method**: rollback.
- Checked `Exception` thoát ra: **không tự rollback theo mặc định**; cần cấu hình `rollbackFor` nếu muốn.
- Method kết thúc bình thường: Spring thử commit. Nếu DB/JPA lỗi lúc flush/commit, commit không thành công và exception vẫn có thể xuất hiện **sau dòng `save()`**.

`AppException` trong mini project của bạn `extends RuntimeException`, nên nếu nó thoát ra khỏi method transactional qua proxy, Spring mặc định rollback. Nhưng nếu bạn **bắt rồi nuốt** một lỗi nghiệp vụ trong method và trả về bình thường, proxy có thể coi là thành công và commit; đừng lấy `try/catch` làm cách giấu lỗi. Riêng lỗi DB/JPA có thể đã đánh dấu transaction rollback-only, nên không được suy ngược rằng mọi exception bị bắt đều chắc chắn commit. [Spring: Rollback rules](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/rolling-back.html).

```java
@Transactional(rollbackFor = SomeCheckedException.class)
public void process() throws SomeCheckedException {
    // Dùng khi một checked exception cụ thể cũng phải hủy toàn bộ thao tác ghi.
}
```

Đây là ví dụ về quy tắc, không phải yêu cầu thêm `rollbackFor` bừa bãi vào mọi method.

## 8. Hai giới hạn hay bị hiểu sai

### 8.1. Gọi nội bộ không đi qua proxy

```java
public void handle() {
    this.createCategoryAndProduct();
}

@Transactional
public void createCategoryAndProduct() { /* ... */ }
```

Nếu `handle()` **không có transaction riêng** và `this` gọi method annotated ngay trong cùng object, lời gọi không đi qua proxy ở chế độ mặc định, nên annotation trên method được gọi **không mở transaction như bạn tưởng**. Cách đơn giản là đặt `@Transactional` lên method Service công khai mà bean khác gọi, hoặc tách nghiệp vụ thành một bean được inject. [Spring: `@Transactional` và self-invocation](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html).

### 8.2. Transaction chỉ bao phủ tài nguyên tham gia

Transaction DB **không tự thu hồi** email đã gửi, file đã upload lên S3, hay HTTP request gửi sang dịch vụ khác. Nếu lưu Product rồi gửi email trước commit, email có thể đã ra ngoài dù DB sau đó rollback. Cần thiết kế riêng cho side effect ngoài DB; bài này chỉ yêu cầu nhận diện giới hạn, không học outbox/distributed transaction.

Transaction cũng không thay thế `WHERE` đúng, `UNIQUE`, FK hay `CHECK`. Nó gom nhiều thao tác lại; **tính đúng của từng thao tác** vẫn cần quy tắc riêng.
