# M2-3 Flyway · Lesson 01: phân tích tình huống schema và lịch sử

> Đề viết lại ngày 2026-10-13. Chế độ LESSON: **8 câu × 5đ = 40đ**; đạt từ 34/40. Khoảng 45–60 phút. Trọng tâm suy luận, không học thuộc định nghĩa. Mỗi câu độc lập; trả lời bằng lời, sơ đồ hoặc SQL ngắn. Không cần cài/chạy Flyway.

## Quy ước để không phải đoán

- Đây là mô hình minh họa cho shopcore, không khẳng định DB thật đã được tạo.
- Chỉ có versioned SQL migrations trong `db/migration`; prefix V, separator `__`, suffix `.sql`. Không có callback, repeatable, baseline, target hay cấu hình đặc biệt, trừ khi câu hỏi nói rõ.
- History mỗi DB độc lập. History thành công phản ánh SQL đã áp dụng, trừ câu cố ý mô tả schema bị sửa tay.
- App dùng Flyway chuẩn bị DB khi khởi động, sau đó JPA kiểm schema; **Hibernate không tự update schema**. Không có code tự gọi migrate trong HTTP handler.
- Không yêu cầu viết dependency, YAML, repair, rollback migration hoặc pipeline CI. Đó chưa phải phạm vi bài này.
- Mọi số checksum bên dưới chỉ là nhãn minh họa, không cần tính thuật toán.

## Câu 1 — Cùng repo, nhưng cột mới không xuất hiện (5đ)

Repo hiện có:

```sql
-- V1__create_products.sql
CREATE TABLE products (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name TEXT NOT NULL
);

-- V2__add_description.sql
ALTER TABLE products ADD COLUMN description TEXT;
```

| DB | URL rút gọn | History | Cột thực tế |
|---|---|---|---|
| Dev | localhost:5432/shopcore_dev | V1, V2 thành công | id, name, description |
| Deploy | db.internal:5432/shopcore | V1 thành công | id, name |

Entity mới có `description`. Lần migrate vừa chạy kết nối **shopcore_dev**, còn app deploy đọc **shopcore**. Đồng đội nói: “Repo có V2 rồi, dev chạy được rồi, deploy chắc chắn có cột; cứ restart Controller.”

Hãy nêu **(a)** sai ở suy luận nào, **(b)** DB nào đã được thay đổi và DB nào chưa, **(c)** bước xử lý vào đúng DB, **(d)** hai bằng chứng cần kiểm sau xử lý, **(e)** vì sao chỉ thêm field Entity không giải quyết được tình huống này.

**Trả lời:**
repo đã có v2 rồi nhưng mà phĩ xem môi trường mình chạy là gì , ở môi trường DEV thì chạy được 2 VErsion , còn deploy thì mới cóc1 nên là không đúng , dev chạy được v1 , v2 rồi thì vẫn chưa chắc chắn được deploy chạy được , thêm field Entity không giải quyết được vì thằng hibernate lúc mà ở Deploy thường thì chỉ là validated th chứ k can thiệp vô được là entity có cột mới  nên là cần phải giải quyết version cho đúng , trường hợp này gặp tôi thì Deploy cần phải được chạy thêm V2 mới nhất nx là dc . Flyway sẽ có cơ chế kiểm tra cái history migration để biết được và đã áp dụng version nào và ở Dev thì sẽ có update thêm cột description , chắc vậy

## Câu 3 — Merge hai migration có phụ thuộc (5đ)

DB dùng chung mới có V1 tạo products(id, name). Hai nhánh thêm:

```sql
-- Nhánh An: V2__add_description.sql
ALTER TABLE products ADD COLUMN description TEXT;

-- Nhánh Bình: V2__index_description.sql
CREATE INDEX idx_products_description ON products(description);
```

Hai file chưa chạy trên DB cần giữ nào, chưa phát hành; các DB thử riêng nếu có đều bỏ được. Không có version khác ngoài V1. Team định giữ cả hai tên trên, hoặc đổi tên bất kỳ một file thành V3 cho hết trùng.

**(a)** Vì sao khác mô tả vẫn có vấn đề? **(b)** Chọn chính xác file nào là V2, file nào là V3. **(c)** Giải thích phụ thuộc SQL khiến việc đổi bất kỳ một file chưa đủ an toàn. **(d)** Nếu V2 thêm description đã phát hành thành công trên DB chung, có được đổi nó thành V3 chỉ để nhường số không? Nêu cách thêm bước index trong trường hợp đó.

**Trả lời:**
khác mô tả vẫn có vấn đề vì là không cho phép có thể trùng version , nếu mà có 2 hay nhiều file. cùng 1 version thì thằng flyway sẽ không biết xử lý sao hết . lúc này team cần phải thống nhất là version nào nên để trước , và trong th này thì nhánh của AN sẽ trước nha , nhánh bình sau , nhưng mà nếu đã lỡ migration trên database rồi thì buộc phải tạo version 3
## Câu 4 — Đặt tên file thêm cột (5đ)

Tình huống riêng: DB đã chạy `V1__create_products.sql`, tạo bảng products(id, name). Bạn muốn thêm cột description kiểu TEXT, cho phép NULL. Chưa có migration nào sau V1.

Bạn tạo file:

```sql
-- V2_add_description.sql
ALTER TABLE products ADD COLUMN description TEXT;
```

1. Tên file này đúng quy tắc mặc định chưa? Viết lại tên đúng.
2. Dòng SQL trên thay đổi gì trong bảng products? Có xóa bảng cũ không?
3. Sau khi migration chạy thành công, Flyway ghi nhận ở đâu để lần sau biết file đã chạy?

Không hỏi option cấu hình kiểm tên hoặc cách xử lý migration thất bại.

**Trả lời:** sai quy tắc nha , __ 2 dấu gạch dưới mới đúng và tên cuả nó sẽ là V2__add_description.sql
dòng trên thay đổi là nó sẽ thay đổi table products bằng cách thêm cột description , khi àm thêm vô thì value nó sẽ là null hết và cần phải truyền data vô đây , thường là version sau sẽ thêm constraint non null cho nó 
sau khi chạy thành công thì ở bảng history thì sẽ có cái là đã áp dụng thì ở version 2 sẽ được đánh dấu là đã áp dụng 

## Câu 5 — Thêm field Entity thì phải làm gì với DB? (5đ)

Tình huống riêng: DB chung đã chạy V1, bảng products có id và name; dữ liệu cũ cần giữ. V1 không bị chỉnh sửa. Code mới thêm field description vào Entity. Hibernate chỉ kiểm tra schema, không tự thêm cột.

Đồng đội đề nghị sửa nội dung V1 để CREATE TABLE có thêm description rồi restart app.

1. Bạn có đồng ý sửa V1 đã chạy trên DB chung không? Vì sao?
2. Muốn thêm description kiểu TEXT cho phép NULL, hãy viết **tên file migration mới và một dòng SQL**.
3. Sau khi áp dụng migration mới, dữ liệu id/name cũ có cần xóa để tạo lại không?

Chưa cần giải thích repair hoặc cách khôi phục checksum mismatch.

**Trả lời:**không vì là nguyên tắc là không được phpes thay đổi version cũ đã được áp dụng vô database , flyway sẽ có cơ chế checksum để xem các bản version cũ đã được áp dụng thì nó sẽ kiểm tra , nếu thay đổi thì sẽ bị mismatch checksum thì nó sẽ k cho khởi động application thàn hcongo . nếu muốn description kiểu TEXT cho phép NULL thì để là 
V2__add_column_description.sql 
code là 
ALTER TABLE products
ADD column description TEXT
sau khi áp dụng migration mứoi thì dữ liệu cũ vẫn còn được giữ lại 

## Câu 6 — Checksum giúp phát hiện điều gì? (5đ)

Tình huống riêng: V1 đã chạy thành công. Bảng history lưu checksum của file tại thời điểm đó. Sau này có người sửa nội dung V1 trong repo; Flyway báo checksum hiện tại khác checksum đã lưu.

1. Flyway đang so sánh hai thông tin nào?
2. Thông báo đó có nghĩa là Flyway đã chạy lại V1 và cập nhật schema theo nội dung mới chưa? Giải thích.
3. Flyway validate chủ yếu đối chiếu **file migration với history**, hay kiểm tra **tất cả cột DB có giống Entity**? Chọn và giải thích ngắn.

Chỉ cần hiểu ý nghĩa checksum; không cần tính số hoặc viết lệnh sửa lỗi.

**Trả lời:**so sánh checksum , nó sẽ dựa vào file sql version thì nó sẽ dựa vào đó mà xem thử checksum khác nhau hay không . thông báo đó là không chạy lại v1 cũ nhé mà nso đang báo lỗi luôn và mịnh cần phải có hướng giải quyết , nó vẫn để version cũ chứ k áp dụng lại v1 mới . đối chiếu file migration với history thôi , có 1 cái table history migration để quản lý version luôn

## Câu 8 — Flyway chạy khi nào? (5đ)

Tình huống riêng: DB đã có V1, repo có thêm V2 hợp lệ. App được cấu hình để Flyway migrate khi khởi động, sau đó JPA kiểm schema rồi app mới sẵn sàng. Không có code gọi Flyway trong Controller.

1. Kể ngắn gọn việc xảy ra khi **khởi động app**: Flyway biết cần chạy V2 bằng cách nào, và ghi nhận gì sau khi chạy thành công?
2. Khi app đã sẵn sàng, client gọi `GET /api/products`. Request này chạy lại V1/V2 hay chỉ gọi Controller → Service → Repository để đọc dữ liệu?
3. Tắt rồi mở lại app với cùng file và history thành công: Flyway có kiểm tra lại không? Có **thực thi lại SQL** của V1/V2 không? Phân biệt hai việc này.

Không cần kể FilterChain/Jackson hoặc viết code Controller.

**Trả lời:**khi khởi động application ,nó sẽ kiểm tra tỏng bảng history migration , xem thử là còn version nào mà chưa đuọc áp dụng không thì nó kiểm tra thấy V2 chưa được áp dụng thì nó sẽ áp dụng và query để áp dụng vô database , và nhận được sự thay doidor của database sau khi thành công và sẽ có check status là đã áp dụng version này
và khi app đã sẵn sàn rồi thì client gọi request thì nó sẽ khọgo chạy lại V1/V2 mà chỉ gọi controller->service thôi , cái bước khởi động application đã làm bước kiểm tra version rồi nên là khi gọi request sẽ k còn làm việc này nữa
khi tắt r mở lại app cùng file và history thành công thì flywway vẫn kiểm tra lại , nếu đúng thì không thực thi lại SQL , nếu thay đổi gì mới thì thực thi SQL ở version mới , k thực thi lại SQL ở version cũ đã được áp dụng
