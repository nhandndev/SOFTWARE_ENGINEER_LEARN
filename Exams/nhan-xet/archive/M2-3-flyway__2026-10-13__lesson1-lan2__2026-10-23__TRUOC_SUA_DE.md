# M2-3 Flyway · Lesson 01: phân tích tình huống schema và lịch sử

> Đề viết lại ngày 2026-10-13. Chế độ LESSON: **8 câu × 5đ = 40đ**; đạt từ 34/40. Khoảng 45–60 phút. Trọng tâm suy luận, không học thuộc định nghĩa. Mỗi câu độc lập; trả lời bằng lời, sơ đồ hoặc SQL ngắn. Không cần cài/chạy Flyway.

## Quy ước để không phải đoán

- Đây là mô hình minh họa cho shopcore, không khẳng định DB thật đã được tạo.
- Chỉ có versioned SQL migrations trong `db/migration`; prefix V, separator `__`, suffix `.sql`. Không có callback, repeatable, baseline, target hay cấu hình đặc biệt, trừ khi câu hỏi nói rõ.
- History mỗi DB độc lập. History thành công phản ánh SQL đã áp dụng, trừ câu cố ý mô tả schema bị sửa tay.
- App dùng Flyway chuẩn bị DB khi khởi động, sau đó JPA kiểm schema; **Hibernate không tự update schema**. Không có code tự gọi migrate trong HTTP handler.
- Không yêu cầu viết dependency, YAML, repair, rollback migration hoặc pipeline CI. Đó chưa phải phạm vi bài này.
- Mọi số checksum bên dưới chỉ là nhãn minh họa, không cần tính thuật toán.

## Câu 1 — Cùng repo, nhưng cột mới không xuất hiện (5đ)

Repo hiện có:

```sql
-- V1__create_products.sql
CREATE TABLE products (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name TEXT NOT NULL
);

-- V2__add_description.sql
ALTER TABLE products ADD COLUMN description TEXT;
```

| DB | URL rút gọn | History | Cột thực tế |
|---|---|---|---|
| Dev | localhost:5432/shopcore_dev | V1, V2 thành công | id, name, description |
| Deploy | db.internal:5432/shopcore | V1 thành công | id, name |

Entity mới có `description`. Lần migrate vừa chạy kết nối **shopcore_dev**, còn app deploy đọc **shopcore**. Đồng đội nói: “Repo có V2 rồi, dev chạy được rồi, deploy chắc chắn có cột; cứ restart Controller.”

Hãy nêu **(a)** sai ở suy luận nào, **(b)** DB nào đã được thay đổi và DB nào chưa, **(c)** bước xử lý vào đúng DB, **(d)** hai bằng chứng cần kiểm sau xử lý, **(e)** vì sao chỉ thêm field Entity không giải quyết được tình huống này.

## Câu 3 — Merge hai migration có phụ thuộc (5đ)

DB dùng chung mới có V1 tạo products(id, name). Hai nhánh thêm:

```sql
-- Nhánh An: V2__add_description.sql
ALTER TABLE products ADD COLUMN description TEXT;

-- Nhánh Bình: V2__index_description.sql
CREATE INDEX idx_products_description ON products(description);
```

Hai file chưa chạy trên DB cần giữ nào, chưa phát hành; các DB thử riêng nếu có đều bỏ được. Không có version khác ngoài V1. Team định giữ cả hai tên trên, hoặc đổi tên bất kỳ một file thành V3 cho hết trùng.

**(a)** Vì sao khác mô tả vẫn có vấn đề? **(b)** Chọn chính xác file nào là V2, file nào là V3. **(c)** Giải thích phụ thuộc SQL khiến việc đổi bất kỳ một file chưa đủ an toàn. **(d)** Nếu V2 thêm description đã phát hành thành công trên DB chung, có được đổi nó thành V3 chỉ để nhường số không? Nêu cách thêm bước index trong trường hợp đó.

**Trả lời:**

## Câu 4 — File nằm đúng thư mục nhưng không được áp dụng (5đ)

DB đã chạy V1 tạo products(id, name). Repo đặt trong đúng thư mục migration:

```sql
-- V1__create_products.sql: giữ nguyên nội dung đã chạy

-- V2_add_description.sql
ALTER TABLE products ADD COLUMN description TEXT;

-- V3__index_description.sql
CREATE INDEX idx_products_description ON products(description);
```

Cho sẵn quy tắc, không bắt thuộc option: khi kiểm tên nghiêm ngặt **tắt**, file sai naming bị bỏ qua; khi **bật**, Flyway báo lỗi tên sớm. Bỏ qua vấn đề naming, V3 cần description tồn tại thì mới chạy được.

**(a)** Chỉ ra tên sai và tên sửa đúng. **(b)** Với kiểm tên tắt, có thể kết luận V2 đã chạy vì file nằm đúng thư mục không? V3 sẽ gặp vấn đề gì? **(c)** Với kiểm tên bật, lỗi nào được phát hiện trước? **(d)** Nếu chưa phát hành các file mới, sửa thế nào mà không thay đổi V1?

Không cần dự đoán history của migration thất bại hoặc trạng thái transaction sau lỗi.

## Câu 5 — Sửa V1 để thêm cột cho DB đã có dữ liệu (5đ)

DB chung đã áp dụng V1 bản gốc, checksum minh họa `old-101`:

```sql
CREATE TABLE products (id BIGINT PRIMARY KEY, name TEXT NOT NULL);
```

Sau đó dev sửa **ngay file V1 đó**, checksum thành `new-202`:

```sql
CREATE TABLE products (
    id BIGINT PRIMARY KEY,
    name TEXT NOT NULL,
    description TEXT
);
```

DB chung vẫn có dữ liệu cần giữ và chưa có description. Chưa có V2. Bản phát hành với V1 mới chưa chạy ở DB nào khác. Kiểm tra báo checksum mismatch.

**(a)** Mismatch đang so hai thứ gì? **(b)** Restart có biến SQL CREATE đã sửa thành thao tác ALTER cho DB cũ không? **(c)** Nếu DB trống dùng V1 mới còn DB cũ vẫn giữ schema cũ, chúng khác gì? **(d)** Nêu kế hoạch sửa ở mức file và viết SQL ngắn để thêm cột mà không xóa dữ liệu DB chung.

Không yêu cầu dùng hoặc giải thích repair.

## Câu 6 — Validate thành công nhưng query vẫn lỗi (5đ)

Repo và history của DB đều khớp V1/V2; V2 đã thêm description. Không thiếu migration, không đổi file. Sau đó một người chạy SQL tay:

```sql
ALTER TABLE products DROP COLUMN description;
```

History không bị sửa. Flyway validate báo thành công. Query của ứng dụng:

```sql
SELECT id, name, description FROM products;
-- Lỗi: column description does not exist
```

**(a)** Vì sao hai kết quả không mâu thuẫn? **(b)** Validate đã xác nhận loại thông tin nào và chưa xác nhận điều gì? **(c)** Nêu hai bằng chứng phải xem thêm để điều tra. **(d)** Trong giả định hiện tại, restart có khiến V2 tự chạy lại và khôi phục cột không? Giải thích; không yêu cầu viết kế hoạch phục hồi.

## Câu 8 — Phân biệt startup và HTTP bằng code (5đ)

Setup giả định: Flyway chạy lúc khởi động; JPA kiểm schema trước khi app sẵn sàng. Entity cần description, DB mới ở V1 chưa có cột đó; V2 thêm cột hợp lệ. Skeleton dưới đây chỉ thể hiện lời gọi, không phải project cần biên dịch:

```java
// ProductController
@GetMapping("/api/products")
public List<ProductResponse> list() {
    return productService.list();
}

// ProductService
public List<ProductResponse> list() {
    return productRepository.findAll().stream().map(this::toResponse).toList();
}

// ProductRepository: JPA repository; findAll đọc Product từ DB.
```

Đồng đội đề xuất thứ tự:

```text
App sẵn sàng -> client GET -> Controller gọi Flyway chạy V1/V2
-> JPA kiểm schema -> Service -> Repository
```

**(a)** Viết lại thứ tự đúng từ khởi động đến trả JSON cho GET đầu tiên. **(b)** Đặt đúng vai trò Flyway, PostgreSQL, JPA/Repository trong thứ tự đó. **(c)** Nếu migration lỗi, có nên coi app đã sẵn sàng phục vụ GET bình thường theo setup này không? **(d)** Nếu khởi động thành công và gọi GET lần hai, V1/V2 có chạy lại không; thao tác DB lúc GET thuộc loại nào?
